## Entries

## 2026-08-16 · "Critical costs are a supposition, not an actual active cost" · no ID

**What happened.** A design conversation rather than a bug: sporadic costs, critical costs, and the observation that both are *"based on how much money is left available"*. The interesting part is that the app already contained the answer to the hardest bit of it and could not use it.

**The template had modelled this a week earlier, and modelled it in a place that could not be read.** Its five contingencies — laptop, appliance, medical, job loss, repair — arrive as rows that are visible and in no total, which is exactly what "a supposition, not an active cost" means. But the mechanism was `pausado`, and the grouping was two invented **categories**. Both are dead ends for a calculation:

- **`pausado` was doing two jobs.** It means "I switched this off". A possibility was never on. Reading one flag for both, the app cannot tell a row you paused this month from a row that has never happened and may not — and un-pausing a contingency to see what it would cost silently adds 2.100 € to `upfrontCash`.
- **Categories cannot carry arithmetic here.** They are the user's: renameable, deletable, app-wide. A derived figure keying on `esporadicos` breaks the day it is binned, and the taxonomy rules exist precisely to stop code depending on an id the user owns. Confirmed before designing anything: nothing in `derive.ts` referenced either invented id, so they were presentation-only and promoting them would have been a new coupling rather than a formalisation of an old one.

So the axis became a field. `kind: 'fijo' | 'esporadico' | 'critico'`, and every pre-v5 row backfills to `fijo` — the only default that leaves an existing budget's figures untouched, and true besides: every row written before the field existed was in the monthly total, which is what fijo means.

**The near-miss worth recording is that `priority` looked like it would do.** It is already there, it is already `esencial | deseable`, and "esencial" sounds like "committed". It is not: the gym is deseable and still leaves the account on the 3rd, and rent is esencial in a sense that has nothing to do with when it is due. Worse, `priority` already drives the move-in minimum in Muebles, so one edit meant to reclassify a monthly cost would have moved an unrelated figure on another screen. **A field that is nearly right is more expensive than a new one, because the wrongness only shows up in the case you did not test.**

**The target stopped being a number.** Once possibilities are first-class, `Buffer.targetCents` is a stored duplicate of their sum — and the two can drift, which is the failure the template had already dodged once by summing rather than writing `840000`. So the type is gone and `cushion().targetCents` is the sum, everywhere it is read. The v4 → v5 read turns a stored target into a **single possibility carrying that amount**, labelled and noted, rather than dropping it: the figure survives to the cent and lands in the one place that can say what it is *for*, which the old field never could.

**What the split actually buys is two subtotals, not one.** `disponible` (in − fijos − the shopping log) and `margen` (disponible − esporádicos). Before this, a negative balance was one number for two unrelated emergencies: *I cannot pay the rent* and *I cannot also buy clothes this year*. The first is not fixable by cutting anything the app can see; the second is a decision. Printing the same red figure for both was the app answering a question nobody had asked.

**Where the fund contribution goes was the one genuinely arguable call.** It is a regular monthly transfer, so `fijo` by regularity — but the axis is commitment, not regularity, and paying yourself is the first thing that stops in a bad month. Filed `esporadico`, so the 100 € is visible below `disponible` as a choice rather than absorbed above it as a bill. The word reads oddly against a monthly standing order, and the argument is in the template's header so the next reader does not "fix" it.

**Four exclusions, one idea.** `countsMonthly`, `countsUpfront`, `breakdown` and `derived.costes` each drop `critico` separately. That is four chances to forget, and the one that gets forgotten is the one that puts 8.400 € of things that have not happened into `dinero al entrar` — the exact bug the template's `pausado` trick was invented to avoid. It is **not** in the invariant table, because there is no static check that would catch it and a ninth predicted invariant in a table that already has six that have never fired would be noise. It is four assertions in `derive.test.ts` instead, including the un-paused `unico` case.

**A tooling note, because it cost real time.** `npx prettier --write` on one file rewrote 295 lines of a 490-line component. Prettier is not a project tool here — no config, not in `package.json` — and this codebase is hand-formatted in a deliberate style. `git checkout` and re-applying the twenty lines by hand was the fix. **Do not reach for a formatter the repo has not adopted; the diff stops being reviewable and the review is the point.**

**Lesson.** *When the codebase already contains a workaround for the thing being asked for, the workaround is the design note.* The template's paused contingencies were a correct instinct expressed in the only vocabulary available at the time — and the feature request was really the request for that vocabulary.

## 2026-08-16 · The app grew the one thing it had promised never to grow · IND003, IND004

**What happened.** "I need daily cost expenses, so I can track shopping by product, which would then add to the total monthly expense." `CLAUDE.md` said, in three separate places, that there is deliberately no daily expense logging and that Historial must never become a transactions feed. So the first move was not to build and not to refuse, but to separate **the rule from its reason**. The reason was *the app has to stay useful without daily upkeep* — a calculator you must feed every day to trust is one you stop feeding by week three, and then its numbers are worse than no numbers. A shopping log that is **additive and optional** does not violate that: every figure the app had still works with an empty log, the verdict still renders, and nothing on any other screen degrades if you never open Compras again. What would have violated it is making the log the *source* of the monthly costs, so that a week of not logging reads as a week of not spending. It does not: the average divides by days elapsed, not by days logged, so silence lowers the average honestly rather than hiding it.

**The whole design is one question: what does a pile of receipts mean per month?** Three candidate answers, and the two obvious ones are both wrong in a way that only shows up in use.

- *This calendar month.* Literal, and it collapses to near zero every first of the month. For the first week of every month the app would answer a different question than it did on the 31st, and the balance would swing by a hundred euros for reasons that are purely calendrical.
- *The last complete month.* Stable, and it reports **nothing at all** until a month has passed — so the feature is inert for exactly the period when someone is most motivated to use it.
- *Daily average × the length of a month.* Chosen. It exists from the first purchase, it settles as data accumulates, and it is the only one that copes with the fact that nobody buys something every day.

**The window's far end is the load-bearing detail, and it is not the last purchase.** Averaging from the first shop to the *last* shop deletes every quiet stretch: log two big shops a fortnight apart, go on holiday for three weeks, and the average would still read as if you were shopping every fortnight. The window ends **today**. Three weeks of buying nothing is three weeks of not spending, and the average is supposed to notice.

**Scaling by 30,4 is where the money-is-integer-cents rule bites (IND001).** `total / days * 30.4375` is two roundings and a float multiply on an amount. It is stored as the exact fraction `1461 / 48` — 365,25 / 12 — and applied as `round(total * 1461 / (days * 48))`: one rounding, integers throughout. The per-product lines are scaled over the *whole log's* window rather than each over its own, so a bag of ice bought yesterday reports as a bag of ice rather than as thirty a month, and the lines still sum to the headline they are a breakdown of.

**The real hazard was never the arithmetic — it was counting the shop twice.** The user already has, or will have, a `Compra semanal` estimate sitting in Alimentación. Log the actual shopping beside it and the monthly total silently contains both. Three ways out, and the choice matters more than it looks:

- *Let the log replace estimates in any category it touches.* No warning needed, but the app would be deleting a row the user typed, on the strength of one purchase, and the total would move the instant a first item is logged.
- *Add, and say nothing.* Silently wrong, which is the failure mode this whole codebase is organised against.
- *Add, and say so.* Chosen. `overlaps()` finds the case, the tab draws an amber banner with both figures side by side — *49,56 € registrado frente a estimado 200,00 €/mes* — and one button pauses the estimates it names. **Pause, not delete**, because the estimate is still the answer to "what if I stop logging".

The consequence worth writing down: **the correctness of the monthly total now depends on a function that draws a warning.** `overlaps()` is not decoration. If it stops firing — a category filter added carelessly, a status forgotten — the app quietly double-counts food and nothing on screen says so. It has its own tests, including the negative one: paused, blank, `shouldNotPay`, `único`, `entrada` and furniture rows must produce no warning, because none of them is in a total to begin with.

**A `Purchase` is not an `Entry`, and the temptation to make it one was strong.** `Entry` is the universal unit and it has paid for itself repeatedly. But a receipt has no frequency (it happened once, on a day), no priority (you already bought it), no status (`pagado` is the only one it can be) and no `history` — a price you paid is not an estimate you can revise, and pushing a revision onto it would put a typo correction into the changelog that IND002 exists to protect. Four of the six fields would have been decoration, and the one that isn't would have been actively misleading. **Reusing a type that fits five sixths of the case is how a model quietly stops meaning anything.** What the two do share is the category axis, and that is exactly the part that had to be shared for the log to reach the breakdown.

**Blank is zero here, and that is a reversal of the app's own rule, argued rather than assumed.** Everywhere else a blank amount is modelled explicitly, because the seeded checklist ships without prices and blank is a normal, lasting state. On a purchase, blank exists for the second between pressing *Apuntar compra* and typing what you paid, and zero is the one amount a real purchase cannot be. So zero *is* the blank: it renders as the same dashed `— —`, it is counted as missing rather than as free, and the type carries the argument in a comment so the next reader does not "fix" it by adding `hasAmount`.

**IND003 was silent, and it should not have been.** Adding `Scenario.purchases` is a new field that needs a read-time backfill, which is the entire case that check exists for — but its parity pass only walks the depth-1 keys of `DEFAULTS()`, and a scenario's fields sit one level below that. The suite caught it instead, immediately: six failures the moment `ensureScenario` handed `undefined` to code expecting an array. Worth recording in the recurrence table as a *miss* rather than a hit, because it maps the check's real coverage: **IND003 guards the top of the payload and nothing under it**, and everything under it is guarded by tests or by nothing.

**Then IND004's habit showed up in a place it does not apply.** The instinct to route every sum through `toMonthly()` is right for entries and wrong for purchases — a purchase has no frequency to mix. `sumAmounts()` says so in its own doc comment, and lives in `lib/` rather than as a `.reduce()` in the component, which is also what keeps the static check quiet without a suppression comment. **The cleanest way to satisfy a heuristic check is usually to stop doing the thing it is heuristically detecting.**

**Verified by driving the packaged build, and the driver lied in exactly the documented way — fourth occurrence.** Two purchases entered through the real UI committed fine; the same recipe on a Costes amount cell did nothing, three times, and the totals stayed put. Not a regression: **an Electron window that is not the OS-focused window dispatches no `focus` or `blur`**, so every commit-on-blur path is inert — the entry below this one records the same thing, and `Emulation.setFocusEmulationEnabled` is the fix. The tell was that the *first* run's window took focus and committed, and the *second* run's did not. Seeding the state through `localStorage` and reloading was the faster route to the thing actually under test, which was the warning banner and its button, not React's input plumbing. **When a harness fails on a path the product already shipped, suspect the harness — it is now four for four.**

**What the driver did find, once it stopped lying:** the amount column was too narrow and clipped its own value (`45, €`), and the trailing `€` unit span the Costes grid carries renders as a *second* euro sign once the column is wide enough to show `formatEUR`'s own. Costes has that same duplication today and gets away with it only because its narrower column cuts the first one off. Fixed here by dropping the span rather than by narrowing the column, and left alone in Costes — a cosmetic defect in a shipped screen is not this change's to fix, but it is this change's to not replicate.

**The mobile fork was the follow-up, and its trigger is a new one.** Costes was forked at 820 px because a nine-column, 1080 px grid cannot be made to work on a phone — a width problem. Compras fits in five columns and scrolls sideways like Historial's table does, so by the existing rule it did not qualify. It was forked anyway, because **the deciding factor here is *when* the screen is used, not how wide it is**: the shopping log is the only part of this app touched standing in a shop, several times a week, and the column you came to type — `IMPORTE` — was second from the right behind a scroll. A screen used daily on a phone earns a phone layout at any width. Two things fell out of the fork that the desktop version does not want: cards **grouped by day** with the day's total in the header (one shop is four lines entered together, and *what did today cost* is asked at the till), and the **monthly equivalent** rather than the total in the sticky footer, since the total is not comparable to anything else in the app. The `.room` group header and the `.mcard` grammar were both reused as they are; the only new CSS is a dash-coloured edge for a row whose amount has not been typed yet.

**Lesson.** *A documented "never" is a compressed argument, and the argument is the part that has to be checked.* "No daily logging" meant "the app must not require daily upkeep to be correct" — which an additive, optional log does not violate, and which a log feeding the primary figures would have. Reading the rule literally would have refused a reasonable feature; reading it carelessly would have built the version that breaks the app the first week it is not fed.

## 2026-08-15 · A spreadsheet became a template, and three of its rows nearly cost 8.400 € on day one · no ID

**What happened.** A `PRESUPUESTO MENSUAL · Madrid` sheet — the budget that already existed outside the app — was turned into a loadable scenario. Most of it is transcription. Three decisions in it were not, and each had a plausible wrong answer that produces a number the app would state confidently and falsely.

**The catastrophe column is not a column of costs, and modelling it as one is the trap.** Five rows — laptop 2.100 €, appliance 400 €, medical 500 €, job loss 5.000 €, repair 400 € — that sum to the 8.400 € fund target. The obvious translation is five `único` entries at `pendiente`. `countsUpfront()` accepts exactly that: one-off, salida, not paid, not paused, has an amount. So `dinero al entrar` would have read **8.400 €**, and `runwayMonths` would have divided savings-minus-8.400 by the deficit. **The app's most load-bearing figure, wrong by the entire size of the emergency fund, with nothing on screen looking off.** They arrive `pausado` instead, which is precisely what the status is for: a row you keep without counting it. The test that asserts `upfront().cashCents === 0` exists for this one case and nothing else.

**The related question — where does the *target* live — the type had already answered.** `Buffer` is a target and only a target, and the 100 €/mes that builds it is an ordinary monthly Entry, not a field. That decision was made months ago for totalling reasons and it turned out to be exactly the shape a real sheet has: one contribution line, one goal, and a pile of reasoning behind the goal. Worth noting because it is the second time the "Entry is the universal unit" call has paid for itself at a moment unrelated to why it was made. The target is *summed* from the five paused rows rather than written as `840000`, so the two can never disagree.

**"Use these categories" had two readings and neither was right alone.** The sheet groups by *nature* — fijos, esporádicos, catástrofe — while the app groups by *domain* — vivienda, alimentación, suministros. Adopting the sheet's three wholesale means Alquiler is no longer under Vivienda and the app's own axis stops existing. Mapping everything onto the domain axis loses the two groupings the sheet was built around, and twelve rows collapse into Otros. The resolution: **the domain axis wins wherever a row genuinely has a domestic home, and a new category is created only where the app has nowhere to put something.** So `Gastos esporádicos` and `Fondo de emergencia` are added; `Gastos fijos` is not, because every one of its rows already had somewhere better to be. The visible consequence, and the one to check against real use: `Ocio y salidas` files under `Ocio`, so that bar reads 130 € where the sheet's column says 190 €.

**An empty category would have been the tell.** The first draft added all three groups, which made `Gastos fijos` a category with zero rows in it — a heading with nothing under it, arriving pre-broken. **A grouping that comes out empty is the axis telling you it is redundant with one you already have.**

**Seeding `history` is not decoration.** Rows could have arrived with `history: []` like the checklist's do. Then the first edit pushes one revision, `drift()` needs `length > 1` to report anything, and the *original* figure — the sheet's, the one worth measuring against — is never in the log at all. The template's amount **is** the original estimate, so it has to be the first revision (IND002). The checklist gets away with an empty history precisely because it has no amounts: there, the first thing typed genuinely is the original.

**On baking numbers into the repo.** `CLAUDE.md` says no rate, cap or price is hardcoded anywhere, and this module hardcodes twenty-two. The rule is not "no numbers" — it is that a *published* figure baked into a repo goes stale within a year and reads as authoritative anyway. These are one person's estimates of their own budget, arriving as a revisable first revision in a log designed for revising them. The distinction is written into the module header rather than left to be re-derived by whoever reads it next and reasonably concludes the rule was ignored.

**Lesson.** *Transcribing a document is a modelling exercise wearing a data-entry costume.* Every column of that sheet had a shape in the app already; the work was deciding which, and the one that would have been silently wrong — five contingencies as pending one-offs — is the one that looks most like a straight copy.

## 2026-08-15 · "The scenario name should be editable" — it was, three screens away · no ID

**What happened.** Reported as a missing feature. The field had shipped from the start: Ajustes → *Números del escenario* → first input, writing through `patchScenario({ name })`. So the honest reading of the report is not "add an input", it is **the name is read in the header picker and changed in Ajustes, and nobody crosses that gap looking for a rename.** An affordance that exists somewhere else is, from the user's side, indistinguishable from one that does not exist. Same shape as the dead-button report below: the complaint named the wrong thing, and taking it literally would have added a second rename field while leaving the reason unfixed.

**Looking at the real one turned up the actual defect.** The Ajustes field wrote the name on every keystroke, straight through `patchScenario`, which meant it bypassed `uniqueName()` — the rule added *that same day* for exactly this failure. Adding scenarios could no longer produce two identical picker options; renaming one onto another's name still could, by hand, in about four seconds. **A rule applied at every call site is a rule with a hole in it, and the hole is always the call site added before the rule existed.** The fix is not vigilance: `patchScenario` now takes `Omit<Partial<Scenario>, 'name'>`, so the only door to a name is `renameScenario`, and the compiler is what says so.

**Commit-on-blur is forced by the rule, not chosen for taste.** The store can hand back a *different* name than the one typed — it dedupes, and it refuses a blank. Keystroke-level writes would mean typing "Piso" next to an existing "Piso" mutates to "Piso 2" on the `o`, and then to "Piso 2 2" as you keep going. So the input holds a draft, commits on blur or Enter, and then drops the draft to re-read the stored value — which is what makes the snap-to-`Piso 2` legible as a result rather than as the field fighting you.

**The bug found on the way: `blur()` runs before React re-renders.** `EditableAmount` had handled Escape as `setDraft(null); blur()`. `setDraft` is queued; `blur()` fires its handler *synchronously*; that handler reads `event.target.value`, which is still the typed text in the DOM. **Escape committed.** It had behaved identically to Enter since the component was written, and on an amount that means Escape silently pushes a price revision (IND002) — the one thing the commit-on-blur design exists to ration. Copying the pattern into the new input is what surfaced it; nothing about the amount cell had changed. Both now set a `cancelled` ref that the blur handler consumes. **Cancel that routes through the thing it is cancelling has to carry state across the hop** — clearing the source of truth is not enough when the DOM is what gets read at the other end.

**Verified by driving the packaged build, and the driver lied first — again.** The CDP script reported that *nothing* committed: not Enter, not clicking away, not the Ajustes field, and an amount cell that would not even reformat to `123,45 €`. Four independent paths failing at once is not four bugs, it is one wrong assumption about the harness. It was this: **an Electron window that is not the OS-focused window does not dispatch `focus` or `blur`.** `element.focus()` still sets `document.activeElement` — which is why the probe for "is the field focused" said yes — but no event fires, so every commit-on-blur path is inert and reads precisely like a feature that was never wired up. `Emulation.setFocusEmulationEnabled {enabled:true}` fixes it in one line, and `document.hasFocus()` is the one-line probe that would have said so immediately. Two smaller ones from the same session: `Runtime.evaluate("location.reload()")` tears down the websocket, so reloads have to go through `Page.reload`; and `.hdr-grp select` matches Situación as well as Escenario, so read the picker by `aria-label`. **Third time a driver script's own defects have been reported to me as product bugs** — the standing fix is to prove the harness can observe a *known-good* behaviour before trusting it about a new one.

**The Escape claim was checked in both directions rather than reasoned about.** Reverting just that handler, rebuilding, and driving it: pre-fix Escape left `123,45 €` in the cell with `history.length: 1`. Post-fix: `— —`, `hasAmount: false`, `history.length: 0`. Worth the four minutes — the argument for the bug was a claim about React's batching versus synchronous event dispatch, which is exactly the kind of thing that is easy to be confidently wrong about.

**Lesson.** *"Feature X doesn't exist" often means "feature X isn't where I look for X".* Worth checking the report against the code before building anything, because the two readings — add it, or move it — produce completely different work, and only one of them also found the hole in the naming rule.

## 2026-08-15 · "El botón de nuevo escenario no funciona" — it worked, and had for months · no ID

**What happened.** Reported straight after the blank-scenario change: the button does nothing. It did something. It had always created the scenario, activated it and added it to `compareIds`. What it never did was create one you could *tell apart* — `App.tsx` called `store.addScenario(es.scenario.firstName)`, so every scenario was named "Mi primer escenario", and the header picker lists names. Three presses, three identical options, three identical screens.

**The bug is older than the change that revealed it, and that is the point.** Before, a new scenario arrived holding 77 seeded rows, so the grid visibly repopulated and the button read as working. That feedback was **incidental** — a side effect of seeding, not anything the button did — and making scenarios blank removed it, leaving the real defect with nothing left to hide behind. **A feature can be carried for months by a side effect of an unrelated one; removing the unrelated one is what files the bug report.** Which is also why the report pointed at the wrong feature: nothing in the new-scenario path had been touched.

**Verified before fixing, then verified again after.** The same `app://movingout` driver from earlier in the day: click the real button, read `localStorage`. Before — `count` 1 → 2 → 3, `names` all `"Mi primer escenario"`, picker unchanged. After — `Escenario nuevo`, `Escenario nuevo 2`, picker following each time. Worth doing in that order: "it does nothing" and "it does something invisible" are the same complaint and want opposite fixes, and guessing between them from the report alone is how you end up debugging `setState`.

**Three more instances of the identical shape, found by looking rather than by being told.** Duplicating twice gave two `Piso (copia)`; adding categories or rooms gave a stack of `Categoría nueva`. All four are "add something from a fixed default label into a list the user reads by label", so all four now go through `uniqueName()` in `src/lib/naming.ts`. It lives in the store rather than in the callers because the store is the only thing that knows what is already called what — and putting it in the four call sites would have made a fifth one wrong later.

**Lesson.** *Blank state is not the absence of design.* Emptying a screen removes whatever was accidentally serving as confirmation, and every affordance that was relying on content to prove it fired has to get that proof back explicitly. Worth re-checking the rest of the app against this: the buttons whose only feedback is that something appears.

## 2026-08-15 · Categories became data, and IND003 fired for the first time · IND003

**What happened.** The ten categories and five rooms were closed unions in `types.ts`. They are now `Taxon[]` lists in `SavedState`, editable from Ajustes, and a new scenario arrives with no entries at all instead of the 77-row checklist.

**IND003 caught the missing backfill, on the first edit, exactly as designed.** Adding `categories` and `rooms` to `DEFAULTS()` blocked the write: *"DEFAULTS defines `categories` but ensureShape never backfills it"*. The check is a crude one — it parses the depth-1 keys of the `DEFAULTS()` literal and greps `ensureShape`'s block for each name — and crude was enough. This is the **second** invariant to earn its place rather than be predicted into existence, and worth noting *why* it fired here when it never fired during the build: the original schema was written in one sitting, where defaults and backfill are the same thought. It fires when a field is added months later, which is the case it was written for and the case that had never happened yet.

**The rename/re-file split is the whole design.** A category has an opaque generated id and an editable label, and entries store the id. That makes renaming free — "Ocio" → "Caprichos" re-titles the group and moves nothing — and it keeps a renamed category comparable with itself across scenarios in Comparar. The alternative, storing the label on the entry, is simpler until the first rename, at which point it is a bulk migration that silently splits history.

**Deleting is where a category editor actually gets dangerous, and the fallback is what defuses it.** Three options were on the table: block the delete while in use, delete the rows with it, or re-file them. Re-filing onto `Otros` was chosen, which then forces `Otros` to be undeletable — and *that* is the constraint the rest leans on. `removeTaxon` always has somewhere to put displaced rows; `storage.ts` always has something to coerce a dangling id onto; the Costes `<select>` can never be empty. One guaranteed row is doing a surprising amount of load-bearing work, so its bin is rendered visibly disabled rather than simply doing nothing when clicked.

**`room` re-files rather than clears, and the reason is a one-line function elsewhere.** `isFurniture(entry)` is `entry.room !== undefined`. So the obvious cleanup on deleting a room — clear the field — would move every article in it out of Muebles and into the Costes grid, as ordinary conceptos, with no error anywhere. **A field that means "which group" and a field that means "which tab" being the same field is the kind of coupling that only bites at deletion time.** Recorded because the same trap is waiting for anything that later makes `projectId` deletable.

**Two things the type change gave up, deliberately.** `Category` is now `string`, so the compiler no longer proves a category exists — the guarantee moved to `ensureShape`, at read time. And `es.category` lost its exhaustiveness check over the full set; it now `satisfies Record<DefaultCategoryId, string>`, covering only the shipped ids. Both are the correct trade for a list the user owns, but they are real losses: the failure mode moved from "won't compile" to "a row lands in Otros", which is quieter. That is why the backfill has its own tests rather than being assumed.

**Verified by driving the packaged build, not the dev server.** Following the 2026-08-11 lesson: a script loaded the real `dist/` over `app://movingout`, cleared storage, and drove the actual DOM — blank first run, add, rename, checklist load, delete-with-refile, reload. It caught two things tests would not have: the row layout stretched to 1400 px, stranding each count and bin at the far edge of the panel, and one probe of my own indexed the last bin in the list *after* a new category had been appended below `Otros`, reporting the fallback as unlocked when it was not. **The app was right and the check was wrong** — worth remembering that a driver script is also code, and its failures read exactly like product bugs. Two Electron re-learns, both already in this log and both hit again: `ELECTRON_RUN_AS_NODE=1` is inherited from VSCode and has to be unset, and `executeJavaScript` calls share one global scope, so a second `const rows = …` throws a redeclaration that surfaces only as "Script failed to execute".

## 2026-08-15 · "The desktop app won't open" — it was opening the whole time · no ID

**What happened.** Reported as: works on the phone, will not open on the laptop. The suggested fix was a laptop-specific branch. There was no bug in the app, and the branch would have forked a working codebase away from the one thing that was actually fine.

**What it actually was, in two parts.** The `.AppImage` in `release/` genuinely cannot run here — no `libfuse.so.2`, no sudo — and it is by a distance the most double-clickable file in that directory. It had been left there on the reasoning that it stays useful on machines that *do* have FUSE. That reasoning is true and it was still the wrong call: **a known-broken artifact sitting next to working ones is not neutral, it is the default thing someone will try.** It is now removed from `build.linux.target`; `tar.gz` is the only artifact. Second, the window opens on **whichever workspace the launcher happened to be on** — during diagnosis it sat on workspace 3 while the current desktop was 4. A window you cannot see is indistinguishable from a window that was never created.

**How it was actually settled, and why the earlier checks were not enough.** Three levels of evidence, each of which looked sufficient and wasn't:

1. *The process stays alive* (`timeout 12 ...; exit=124`) — passes for a process that never opens a window.
2. *A window exists* (`wmctrl -lG` → `2560x1464` at `+60+256`, on-screen, `_NET_WM_WINDOW_TYPE_NORMAL`) — passes for a blank white window.
3. *The DOM has content* — the only one that answers the question.

Level 3 needed no code change: launch the **packaged** binary with `--remote-debugging-port=9222`, then drive the DevTools protocol over a WebSocket (`suppress_origin=True`, or the handshake is refused with a 403 naming `--remote-allow-origins`). That returned 249 nodes, 405 CSS rules, `getComputedStyle(body).backgroundColor === rgb(239,237,231)` — the real `--bg` — and `localStorage` working at `origin=app://movingout`. **This is the check that should have been run on the packaged build on day one**; the `capturePage` hook from 2026-08-11 only ever proved the *dev* build renders, and dev is the configuration where the asar does not exist.

**The theory that was wrong, and worth recording because it was plausible.** The suspicion was that `net.fetch(pathToFileURL(...))` cannot read through `app.asar` — Chromium's `file://` loader has no idea what an asar is — so the packaged app would serve nothing and show a blank window, exactly matching the symptom, and *only* when packaged. It is a real failure mode for this design. It is simply not what happens: Electron's `net.fetch` resolves inside the archive, and the origin fix holds in the packaged build. Recorded so nobody re-derives the fear and "fixes" it by disabling asar.

**Lesson.** *Works on A, not on B* invites a fork, and a fork is almost always the wrong first move — it doubles the surface while leaving the cause untouched. The useful question is what genuinely differs between A and B, and here nothing in `dist/` did: the difference was the host, the artifact chosen, and which workspace a window landed on.

## 2026-08-11 · Wrapped as a desktop app and an APK; the origin is the whole story · no ID

**What happened.** The same `dist/` got two native shells: Electron for the desktop and Capacitor for Android. No `src/` file changed. The interesting parts were all outside the app.

**`file://` would have silently emptied the app.** The obvious desktop shell is `win.loadFile('dist/index.html')`, and it would have rendered perfectly. But a `file://` page has an **opaque origin**, and Chromium keys `localStorage` to an origin — so the store this app keeps *everything* in (every scenario, every price revision, the whole seeded checklist) would have been unreliable, and unreliable in the worst way: fine within a session, empty or orphaned across launches. The fix is to give the shell a real origin — `app:` registered via `registerSchemesAsPrivileged` as `standard` + `secure`, serving `dist/` from `app://movingout`. Capacitor already does the equivalent, serving from `https://localhost`. **The lesson generalises past Electron: when a web app is rehosted, the origin moves with it, and anything keyed to the origin moves too.** `IND006` says `localStorage` has exactly one door in `storage.ts`; it does not say the room can be moved out from under it.

**`app.commandLine.appendSwitch('ozone-platform', 'x11')` does nothing.** Chromium's Wayland backend segfaults on this compositor before it paints a frame, and X11 is stable. The natural place for that switch is the top of `main.cjs` — where it has no effect at all, because ozone selects its backend before the main script is evaluated. The switch has to arrive on the command line, so it lives in the npm scripts and in `build.linux.executableArgs`, with a comment in `main.cjs` explaining why it is *not* there. Two runs looked identical (`SIGSEGV`) and it would have been easy to conclude the flag didn't work rather than that it arrived late.

**Verify a GUI by capturing it, not by watching it not crash.** "The process is still alive after 10 seconds" was the check available, and it is a weak one — it passes for a blank white window. Adding a temporary `capturePage()` + `executeJavaScript('document.querySelectorAll("*").length')` hook proved 194 nodes and the right `<title>`, which is what actually established that the shell renders the app. Removed once it had answered. Related: `exit=$?` after an `echo` reports the echo. Two "passes" were read off the wrong exit code before the tests were rewritten to report `$PIPESTATUS`/direct codes — `139` (SIGSEGV) and `124` (timeout, i.e. survived) are the two answers that matter and they are easy to hide behind a pipe.

**Packaging is what made the stale palette visible.** The icons were still pre-reskin — ink `#1E1813` and mulberry `#C88ED6` — three months of `tokens.css` edits had never touched them, because baked pixels are not type-checked, not linted and not imported by anything. Android made it worse by shipping its own stock logo. They are now generated by `scripts/make-icons.py`, which reads the `:root` block, so the "swapping the palette is one edit" promise in `CLAUDE.md` covers them. The PWA manifest had drifted the same way and for the same reason. **Anything that copies a token instead of reading one is a future inconsistency**; the three that genuinely cannot read `tokens.css` — the manifest, the Capacitor config, the pre-paint window colour — are now each commented as the exception they are. (`main.cjs` *can* read it, and does.)

**Two environment traps, neither of them the app's fault.** Electron came up as plain Node with every API `undefined`, because VSCode sets `ELECTRON_RUN_AS_NODE=1` for extension-host children and this session inherited it; the giveaway was a `Node.js v24.18.1` crash banner where an Electron stack should be. And the AppImage builds but cannot run here — no `libfuse.so.2`, no sudo to install it — so the shipped desktop path is `release/linux-unpacked/` behind a `.desktop` entry. **An artifact that builds is not an artifact that runs, and the difference only shows up if you run it.**

## 2026-08-11 · Re-skinned to `Independencia`, and two written rules were overturned · no ID

**What happened.** The Claude Design project *Moving out finances app* (`Independencia.dc.html`) replaced the palette, the type stack and several screen layouts. Most of it was a straight port. Two parts were not, because the design contradicts things `DESIGN-SYSTEM.md` had committed to in writing, and a design that disagrees with a doc is only worth adopting if you can say which one was wrong.

**`--blue` now exists, and the old rule was too broad.** The doc said: *"`pagado` and `pausado` get no hue at all … which is why there is no `--info` token."* The reasoning was that neither state is good or bad. That is true of both, but it conflates two different things. `pagado` is a **positive statement of a fact** — this is settled — as are *refundable* and *pago único*. `pausado` is the **absence** of one: a row deliberately excluded from the totals. Facts can carry a colour without being judgements; absences cannot, because any hue turns an exclusion into a verdict. So `--blue` carries the three facts, `pausado` keeps the neutral pill, and the rule is now four semantics rather than three. The old rule was not wrong about `pausado`; it was wrong to extend that to `pagado`.

**Light mode stayed, against the design.** The design ships Papel, Plano and Noche behind a `data-pal` attribute. Only Papel is built. The `data-pal` switch in a `.dc.html` is a *design-tool* affordance — the props panel, so a designer can flip variants in preview — and reading it as a product requirement would have cost a `Settings` field, a storage version bump with an `ensureShape` backfill (IND003) and a contrast pass over eight screens, in exchange for undoing the product's own argument that it commits to one look. Recorded in `DESIGN-SYSTEM.md` §2 with that price attached, so it is a decision rather than an omission.

**Two smaller things the port fixed rather than copied.**

- **Comparar was using the accent to mean "good".** The old screen gave the *best* cell in each row an accent underline, which is exactly the overlap §1 forbids. The design's answer is better and it is the one now built: the accent tints the column of the scenario **you are standing in** — that is interaction, *where you are* — and the per-cell deltas carry green/red by outcome. `FIANZA (DEVOLVIBLE)` is deliberately neutral: a bigger deposit is more cash to find and none of it is lost, so neither direction is better and colouring it either way would be a claim.
- **The `▲ 14 %` chip beside an amount had nowhere to live** in a nine-column grid. Dropping it would have lost the at-a-glance "this moved" signal, so it moved into the revision counter at the end of the row: the button shows the count and takes red or green from the direction of the **last** revision. Same signal, one column cheaper, and it is already the drawer's handle.

**Lesson.** Both reversals came out of the same question, which is worth asking of any design hand-off: *is this contradiction a mistake, or does the design know something the doc didn't?* `--blue` was the second — the doc had over-generalised from one true observation. Noche was the first — a preview affordance read as a product feature. Neither is answerable by looking at the design alone; you have to go back to the sentence in the doc and ask what it was actually protecting.

**A second lesson, and a cheaper one: `node` was on the machine the whole time.** It sits at `/home/p/.local/share/node/bin` and is not on `PATH`, so `command -v node` and a `find / -maxdepth 4` both came back empty and the whole re-skin was written under the belief that it could not be compiled. Substitutes were built instead — a script to check the i18n key graph, another for unused imports, esbuild's native binary to parse every file. They were worth having and they caught two real errors, but they cost time and they proved much less than `tsc` did in one second. **An absent tool is a claim; verify it the way you would verify a number.** One `find / -xdev -name node` would have settled it. `CLAUDE.md` now records the path.

## 2026-08-09 · The empty app claimed you could afford it · no ID
**What happened.** First launch, nothing filled in, and the verdict pill read **✓ Te lo puedes permitir** with a green `+0,00 €` balance. The sixth KPI said the colchón was `Cubierto` — against a target of zero.

**Why.** `verdict()` branched on the sign of the balance and nothing else. With no data, `inCents` and `outCents` are both `0`, so the balance is `0`, which is neither negative nor below 5 % of zero, so it fell through to `ok`. `covered` had the same shape: `savings >= target` is trivially true when the target is `0`.

**Fix.** A fourth verdict, `sindatos`, returned when nothing has been entered on either side, rendered as a neutral `--stone` pill with no hue — it is not a mild yes and not a mild no, it is the absence of an answer, and colouring it would make it one. `covered` now requires a target above zero. Two tests pin it, including one that a genuine 730-in-730-out *does* still answer (`justo`), so the guard cannot swallow a real result.

**Lesson.** The design doc already says this — *"a zero is a claim, a dash is an admission"* — but it says it about **amounts**, and the rule was implemented only there, in `hasAmount`. The same rule applies to every derived figure computed **from** missing amounts. A verdict, a coverage ratio and a buffer status are all claims too, and they all default to the confident-looking answer when their inputs are empty. Worth checking the rest of `derive.ts` against this before adding anything to it: the question is not "does this handle zero" but "can this tell zero from nothing".

## 2026-08-09 · `parseAmount` read `12,999` as twelve thousand · IND001
**What happened.** A test asserting whole cents failed: `parseAmount('12,999')` returned `1299900` (12 999 €) instead of `1300` (13,00 €).

**Why.** The separator heuristic was written once for both separators: *"a trailing group of exactly three digits is a thousands separator, unless the other separator is also present"*. That is right for a dot (`1.695` is one thousand six hundred and ninety-five) and wrong for a comma. In `es-ES` a comma is **always** the decimal separator — there is no reading of `12,999` that means twelve thousand.

**Fix.** Split the rule by separator: with both present the last one wins; a lone comma is always decimal; only a lone dot falls back to the three-digit heuristic. Test pins both readings side by side.

**Lesson.** IND001 is not only about floats. Getting the *locale* wrong produces exactly the same failure mode the invariant was written for — a plausible-looking number that is off by a factor of a thousand, entered by hand and never questioned. The invariant text says "no float arithmetic"; the real rule is "money never goes through a parser you have not tested against the locale you ship".

## 2026-08-09 · `es-ES` does not group four-digit numbers · no ID
**What happened.** Three formatting tests failed expecting `1.695,50 €`. `Intl.NumberFormat('es-ES')` returns `1695,50 €`.

**Why.** Not a bug. CLDR gives `es-ES` `minimumGroupingDigits: 2`, so the thousands separator only appears from five digits: `1695,00 €` but `10.000,00 €`. The expectation was wrong, not the formatter.

**Fix.** Corrected the tests and added one that pins the boundary explicitly, because this app renders four-figure `dinero al entrar` totals constantly and the next person to "fix" the formatting will reach for a hand-rolled separator.

**Lesson.** Reinforces the existing rule rather than adding one: format only through `Intl`. A hand-rolled `,`/`.` swap would have produced confidently wrong Spanish on the single most-read number on the Resumen screen.

## 2026-08-09 · The checker matched its own documentation · no ID
**What happened.** `check.py` reported *"could not parse DEFAULTS() — IND003 is not protecting you"* against a `storage.ts` that had a perfectly well-formed `DEFAULTS`.

**Why.** `check_ind003()` finds the declaration with `re.search(r"\bDEFAULTS\b\s*[=(:]", line)` over every line, and unlike the text checks it does not skip comments. The module's own doc comment said *"a default in `DEFAULTS()` and a backfill in `ensureShape()`"*, so both symbols matched inside prose, six lines above the real code.

**Fix.** Rewrote the doc comment to describe the two functions without naming them in call syntax. `DEFAULTS` is also written as a concise arrow body returning an object literal — `(...) => ({ ... })` — because the key-extraction walks from the first `{` at depth 0, and a `function` form puts the payload keys one brace deeper where they are invisible to it.

**Lesson.** A static check that reads its own file's prose will eventually be defeated by good prose. Worth remembering before trusting an IND003 pass: a *silent* pass could equally mean it matched a comment that happens to contain balanced braces. If IND003 ever fires spuriously again, that is the promotion trigger — teach `check_ind003` to skip comment lines rather than working around it a second time.

## 2026-08-09 · `Buffer` lost two fields to keep Entry universal · IND004
**What happened.** Not a failure — a design decision worth recording because it contradicts a type sketched in `CLAUDE.md`.

`Buffer` was specified as `{ targetCents, monthlyContributionCents, applianceFundMonthlyCents }`. Implementing it that way meant the two monthly contributions were real monthly outflows living outside `entries[]`, so `monthlyTotals()` would have needed a second code path, and the Costes totals row would have disagreed with the Resumen KPI — the exact IND007 failure mode.

**Fix.** `Buffer` keeps `targetCents` only. The reserve contribution and the appliance sinking fund are seeded as ordinary monthly `Entry` rows in `otros`, so they normalise, total, chart, drift and get revised like everything else.

**Lesson.** "Entry is the universal unit" is load-bearing, not a slogan. When a second shape wants to hold money, the question is what it costs to express it as an Entry — and here it cost nothing, while not doing so would have bought a permanent second summing path.
